# peft-lora-memory-and-quality

**LoRA trains 1,178x fewer parameters and saves 5.97x the memory.** Those two
numbers get used interchangeably and they are not close. The gap is the frozen
base weights, which LoRA does not touch — they are **99.6% of the LoRA
budget** and set a floor no rank can go below.

This repo answers one question:

> Does LoRA's memory saving match the closed-form prediction, and which term
> does it fail to reduce?

## The answer

`llama-8b` at rank 16 on `q_proj`/`v_proj`, weights and gradients in bf16,
Adam moments in fp32:

| | full fine-tune | LoRA | QLoRA |
|---|---|---|---|
| weights | 14.96 GiB | 14.96 GiB | 3.74 GiB |
| gradients | 14.96 GiB | 0.01 GiB | 0.01 GiB |
| optimizer | 59.83 GiB | 0.05 GiB | 0.05 GiB |
| **total** | **89.74 GiB** | **15.02 GiB** | **3.80 GiB** |
| trainable params | 8,030.0M | 6.8M | 6.8M |

LoRA removes the gradient and optimizer terms almost entirely — 74.8 GiB of
the 89.7 — and leaves the weights exactly as they were. **QLoRA is the variant
that attacks the term LoRA cannot**, which is why it is a 4x further cut
rather than a marginal one.

## Rank is not the memory knob

| rank | adapter params | LoRA total | vs full |
|---|---|---|---|
| 4 | 1.7M | 14.97 GiB | 5.99x |
| 16 | 6.8M | 15.02 GiB | 5.97x |
| 64 | 27.3M | 15.21 GiB | 5.90x |
| 128 | 54.5M | 15.46 GiB | 5.80x |

A **32x rank sweep moves the total by half a gigabyte.** Pick rank for quality
and let the weight dtype carry the memory — the two decisions are effectively
independent, which is the useful thing to know before a run.

## Target modules matter more than rank

| targets | rank | adapter params | LoRA total |
|---|---|---|---|
| q,v | 16 | 6.8M | 15.02 GiB |
| q,v | 64 | 27.3M | 15.21 GiB |
| all linear | 16 | 41.9M | 15.35 GiB |
| all linear | 64 | 167.8M | 16.52 GiB |

Adapting every linear layer instead of just attention is a **6.2x larger
adapter at the same rank** — a bigger change than a 4x rank increase. The MLP
is where the parameters are, and `all linear` at rank 16 costs more than
attention-only at rank 64.

Full tables: [`results/memory.md`](results/memory.md). Every number is
generated by [`scripts/generate_results.py`](scripts/generate_results.py),
which asserts each claim before writing the file.

## The 5.97x is a short-sequence number

The table above counts weights, gradients and optimizer state. It excludes
activations — and activations behave unlike anything in it. Weights are fixed by
the architecture; activations scale with batch and sequence length, and the
attention term scales with the **square** of sequence length.

`llama-8b`, batch 1, LoRA rank 16:

| sequence | activations | LoRA total | activations are | LoRA vs full |
|---|---|---|---|---|
| 512 | 1.64 GiB | 16.66 GiB | 10% of it | **5.48x** |
| 2,048 | 6.75 GiB | 21.77 GiB | 31% | 4.43x |
| 8,192 | 30.00 GiB | 45.02 GiB | **67%** | 2.66x |
| 32,768 | 168.00 GiB | 183.02 GiB | **92%** | **1.41x** |

**LoRA removes gradient and optimizer state, which do not depend on sequence
length. It does not reduce activations at all** — the forward pass through the
frozen base is unchanged, and backprop still traverses it to reach the adapters.
A fixed saving divided by a growing total is a shrinking ratio.

The ratio decays toward 1.0 and never inverts, because activations are identical
between the two variants. The claim is *the advantage shrinks*, not *LoRA stops
being worth it*.

### Small models hit this first

Sequence length at which activations exceed everything the budget above counts:

| model | parameters | crossover |
|---|---|---|
| `smol-135m` | 0.16B | **1,024** tokens |
| `qwen-0.5b` | 0.63B | 2,048 |
| `llama-1b` | 1.50B | 4,096 |
| `llama-8b` | 8.03B | 8,192 |

This is the opposite of the intuition that fewer layers means fewer activations.
The cause is the **embedding table**: `2 × vocab × hidden` parameters that cost
weights, gradients and optimizer state while producing no per-layer activations.
On `smol-135m` that is most of the parameter count, so its states budget is
large relative to its activation footprint.

The excluded term matters most on the models people prototype with — exactly
where a memory plan is least likely to be checked.

### Checkpointing, not quantisation, is the long-context lever

Longest sequence fitting on one 80 GiB card:

| variant | plain | with checkpointing |
|---|---|---|
| full fine-tune | **does not fit** | does not fit |
| LoRA | 8,192 | **131,072** |
| QLoRA | 16,384 | 131,072 |

Checkpointing takes LoRA from 8k to 128k — a 16x gain — against 2x for
quantising the base. They compose, but the quadratic term is the expensive one
and only checkpointing removes it. It retains **6.7%** of activation memory at
32k, and costs roughly a third more compute, which is not modelled here.

**With checkpointing on, only the token count matters.** Activations become
linear in `batch × sequence`, so batch 4 at 32k and batch 1 at 128k cost
identical memory — the split becomes a throughput and convergence decision
rather than a memory one. Without it, a long sequence at equal token count costs
strictly more.

Full tables: [`results/activations.md`](results/activations.md).
[ADR 001](docs/adr/adr-001-quote-the-budget-with-its-sequence-length.md) records
why memory figures now carry the sequence length they were computed at.

## The arithmetic mistake worth avoiding

**Adam moments are fp32 even when the weights are bf16.** Counting them at 2
bytes understates a full fine-tune by about a third — 30 GiB on `llama-8b` —
which is the difference between a job that does not fit and a job that appears
to. `test_optimizer_state_is_two_moments_in_fp32` pins it.

The second one: grouped-query attention makes K and V narrower than Q. Counting
all four projections at `hidden x hidden` overstates every model here, and
`test_gqa_reduces_kv_projection_size` catches it.

## What this does not cover

- **Activations** are now covered above rather than excluded, but the per-layer
  multiple there is a stated approximation of how many tensors an
  implementation keeps live, not a count from a profiler. It is identical
  across variants, so comparisons between them hold; the absolute figures carry
  that uncertainty.
- **Fragmentation and allocator overhead.** A real run needs headroom above
  these numbers. They are a floor, not a target.
- **Quality.** Nothing here says which rank trains a better model. The claim is
  narrower and, I think, more useful: rank is not the knob you reach for when
  the job does not fit.
- **No training run was performed.** These are closed forms from four integers
  per architecture. That is why the output is identical on any machine — and
  why it is a prediction rather than a measurement.

## Reproduce

```bash
uv sync --extra dev
uv run python scripts/generate_results.py
uv run python scripts/generate_activations.py
uv run pytest
```

Pure arithmetic, no model weights downloaded. CI regenerates the results and
fails on any diff.

## Relationship to production work

An independent reimplementation of the memory-planning half of post-training
work I have done professionally. No employer code, data or configuration — the
model shapes here come from published architecture descriptions and the rest is
arithmetic.
